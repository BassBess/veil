# Database security and privacy

## Keys and unlock

A cryptographic OS random source generates a fresh 32-byte database key for each newly published generation. SQLCipher receives its raw-key format through the counted `sqlite3_key` API. The passphrase and raw key never appear in SQL, shell arguments or Python messages. The app verifies the SQLCipher implementation, invokes its key API, then reads the keyed schema before treating an existing Vault as unlocked. The cipher format uses version 4 compatibility, page encryption and page authentication. Raw binary buffers and the encoded FFI key use zeroizing allocations. The connection has SQLCipher memory security enabled. Copies elsewhere in Rust, JS, IPC, OS services and subprocesses do not have a complete memory-erasure guarantee. [SQLCipher API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)

- **Passphrase.** Minimum 12 Unicode scalar characters, consistent with the existing Rust policy. The wrapper v1 derives a 32-byte wrapping key using Argon2id v0x13, 65,536 KiB, 3 iterations, 1 lane and a fresh random 16-byte salt. AES-256-GCM with a fresh 12-byte nonce wraps the database key. The credential metadata identifies the fixed KDF configuration by version. The legacy Argon2 parameters remain separate.
- **Windows.** DPAPI protects a credential payload scoped to the signed-in OS account. Optional Windows Hello prompts as before. The prompt guards application access and does not change how DPAPI protects the payload.
- **macOS.** The existing Keychain service holds the protected credential payload and the bootstrap holds its item reference. Optional LocalAuthentication uses the device owner's credentials. It is an application gate separate from Keychain access controls.
- **Linux.** Passphrase only. No Secret Service, Windows Hello, or macOS authentication support is claimed.

The active bootstrap is a compact JSON manifest beginning with the versioned SQLCipher marker. Its clear fields include generation UUID, credential mode, necessary KDF metadata or platform, and protected key data. AEAD AAD binds the wrapping version, generation and mode. The protected account payload includes that same binding. Changing the mode flag without an authenticated new wrapper is rejected. The database's first 16 bytes must match the generation identifier used as SQLCipher's explicit salt. The key and authenticated schema are checked separately. A UUID has ample random variation for this use and is public metadata.

The app requires native verification before enabling system sign-in or removing it from a system-authenticated unlocked Vault. Passphrase and mode transitions create a new protected wrapper, independently open the database using that wrapper, then publish it atomically. The active database key stays the same. Changing a passphrase is not data-key rotation. Existing valid bootstrap copies can still open the same database if an actor can replay them and unwrap the key. The app neither supports copy rollback nor has an external monotonic trust anchor. Avoid treating a mode change as protection against someone who already holds recoverable copies or the database key.

Account-key entries are retained where cleaning them could invalidate a recovery copy. The old Keychain implementation provides no active retirement of obsolete user Vault references, and an interruption may leave an unused entry. This requires a platform-aware retention and cleanup procedure. Native prompts are unavailable to a Linux test environment. The OS account modes do not provide hardware-bound key access against malicious same-account processes.

## Storage locations

The application identifier remains `com.tauri.dev`. The app-data directory holds the marker `identities.vault`, the sibling lock `identities.lock`, the active database under `identities.sqlcipher/<generation>/vault.db`, and any encrypted legacy recovery copy. The usual bases are `%APPDATA%\com.tauri.dev` on Windows, `$XDG_DATA_HOME/com.tauri.dev` or `~/.local/share/com.tauri.dev` on Linux, and `~/Library/Application Support/com.tauri.dev` on macOS. Actual directories can be redirected by OS and app configuration. [Tauri PathResolver](https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html)

## Disk safeguards and deletion

- A limited busy timeout and serialized immediate transactions coordinate writers. The shared legacy lock protects the complete unlocked lifetime. On Unix, generated directories and database files are owner-only (0700/0600). Windows relies on the user's profile ACLs and still requires installer verification.
- DELETE rollback journal, `synchronous=EXTRA`, `secure_delete=ON`, `temp_store=MEMORY`, foreign keys, general-row protection and `trusted_schema=OFF` are configured and checked on every app connection. The suite inspects a live rollback journal for a synthetic canary, checks its cleanup, checks temp materialization has no disk filename and checks no WAL/SHM is generated. Journal page encryption does not hide all filesystem metadata.
- Static error strings avoid echoing sensitive SQL arguments or decrypted values. SQLCipher runtime logging is disabled after setting the key and before opening encrypted contents. The standalone probe may show generic wrong-key page diagnostics. Logging of application payloads or parameter tracing would require a separate review.
- Mapping deletion leaves original history. History clearing retains mappings. Named project deletion logically removes its mappings, rules and history while retaining counters. Complete unlocked reset clears active data and counters in a transaction, retaining the current protection mode. Account-capable systems also preserve the established explicit locked reset, publishing a fresh v2 generation and a new database key. It is destructive to the active logical dataset and can leave an unreferenced encrypted prior generation, separate from the migration recovery backup. Linux requires unlock before reset.
- Secure deletion does not guarantee erasure from SSD snapshots, wear leveling, filesystem backups, old database/bootstrap copies, swap or exported documents. For a file-level backup, close the Vault and copy the active marker and its referenced generation together, retaining its needed credential. Check recovery in an isolated app-data directory. No backup writer or destructive automatic cleanup is shipped.

## Confirmed privacy findings outside the database

- `documents.rs` still writes the original DOCX to a temporary file before parsing. Replace this with bounded in-memory input or suitable descriptor transport. A hard termination can leave the full plaintext package. The source document, process memory and any selected exports remain separate from SQLCipher.
- `docx_export.py` still copies unmodified package members, including author metadata. The previous synthetic probe confirmed author text survives even after reviewed body substitutions. A later change should define and test an explicit OOXML sanitization contract for metadata, comments, embedded files, headers outside reviewed spans and other unreviewed package content.

Unlocked process compromise, WebView/IPC exposure, source files, clipboard, exports, model misses and same-user software are outside SQLCipher's at-rest protection. Preserve appropriate user-facing distinctions between pseudonymized, anonymized and sanitized outputs. The database preserves the existing retention contract without proactively discarding full original text or defined custom phrases.
